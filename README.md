# Store Manager's Copilot — Retail Sales & Inventory

A copilot for a store manager running a small retail chain. It answers
plain-language questions about sales and stock with the actual numbers
behind every answer, and proactively flags what needs attention today:
likely stock-outs, stock that isn't moving, and sales spikes or drops
worth a look — each with the data and reasoning behind it.

## What it does

- **Today's attention list** — a dashboard of:
  - **Stock-out risk**: products projected to run out within 7 days, based on
    trailing 14-day sell-through vs. current stock on hand.
  - **Slow movers**: products with meaningful stock but very little sold in
    the last 30 days — candidates for a markdown or a stop-order.
  - **Sales spikes & drops**: products whose recent sell-through has moved
    sharply (≥50%) against their own trailing baseline.
- **Ask the copilot** — a chat box for plain-language questions like
  *"What's running low at T Nagar?"*, *"How did Energy Drink do this
  month?"*, or *"Which products aren't moving?"*. Every answer is grounded
  in the numbers computed above; if the question can't be answered from the
  data, the copilot says so instead of guessing.
- **Store filter** — every view can be scoped to a single store or looked
  at across the whole chain.

## Design choices (what's automated, what isn't, what's left out)

- **Deterministic logic vs. LLM reasoning are fully separate.**
  `src/analytics.py` is plain pandas — it computes every number the app
  ever shows, with no model call involved. `src/llm.py` only decides which
  of those computations answers a given question and phrases the result;
  it is instructed never to state a number that isn't in the data it was
  given, and the prompt is enforced by only ever handing it the specific
  structured "grounding" block that was actually computed (see
  `build_grounding()`), never the model's own general knowledge.
- **No RAG / embeddings.** The source data here is small and structured
  (CSV sales & stock records), so retrieval is a direct, auditable query
  (`analytics.py` functions) rather than a similarity search — this problem
  statement doesn't call for a vector index, and adding one would only make
  the grounding harder to verify.
- **Graceful degradation.** If `GEMINI_API_KEY` is missing or the API call
  fails for any reason (quota, network, timeout), the app falls back to a
  template-rendered version of the same grounded data instead of failing
  the request — the manager still gets a usable, still-fully-grounded
  answer, just less fluently phrased.
- **What's left to a human:** the copilot recommends and explains, but the
  actual reordering, markdown, or promotional decision is left to the
  manager — the system never claims to have taken an action.
- **What's left out on purpose:** no user accounts/auth (single-tenant demo
  for one chain), no write-back to the data (read-only analytics), no
  multi-turn conversation memory (each question is answered independently
  from fresh data) — all reasonable simplifications for a 24-hour build
  that don't compromise the core "grounded answers with evidence" goal.

## Data

All data under `data/` is synthetic, generated by `src/generate_data.py`
(seeded, so it's reproducible — `python -m src.generate_data` regenerates
it). It covers:

- 5 stores across 5 cities (`data/stores.csv`)
- 30 products across 6 categories (`data/products.csv`)
- 90 days of daily sales (`data/sales.csv`) and stock snapshots
  (`data/stock.csv`)

A few scenarios are deliberately engineered into the data so the "difficult
case" is easy to demo:
- **Paneer 200g at the Koramangala store**: sales collapse to near-zero in
  the last 30 days while stock keeps arriving on the normal restock cycle
  → shows up as a slow mover.
- **A product at the Anna Nagar store**: a sudden ~10x demand jump in the
  last 5 days → shows up as both a sales spike and a stock-out risk.
- **A product at the T Nagar store**: a steady upward demand trend over the
  full 90 days → shows up as a spike and a stock-out risk at once.

## Running it

```bash
pip install -r requirements.txt
export GEMINI_API_KEY=your-key-here   # optional — app runs without it, see below
python app.py
```

Then open http://localhost:8000.

- With `GEMINI_API_KEY` set: answers in the chat are phrased by Gemini
  (`gemini-2.5-flash`), strictly from the grounded data.
- Without it: the app still runs and still answers every question, using a
  templated rendering of the same grounded data (a chat message reports
  `grounded · template fallback (no LLM)` in the UI, and
  `"llm_used": false` in the API response, so it's obvious which mode
  produced the answer).

## API

- `GET /api/health` — status check.
- `GET /api/stores` — list of stores.
- `GET /api/briefing?store_id=ST01` — today's attention list (stock-out
  risk, slow movers, sales moves), optionally scoped to a store.
- `POST /api/ask` — `{"question": "...", "store_id": "ST01"}` (store_id
  optional) → `{"answer": "...", "grounding": {...}, "llm_used": true|false}`.
  `grounding` is the exact structured data the answer was based on.

## Project layout

```
app.py                  # FastAPI app — serves the API and the frontend on :8000
requirements.txt
src/
  analytics.py           # deterministic pandas logic — the only source of numbers
  llm.py                  # Gemini-backed phrasing layer + grounded fallback
  generate_data.py        # synthetic data generator (seeded, reproducible)
data/                    # generated CSVs (committed, so no setup step is needed)
frontend/dist/index.html # single-page dashboard + chat UI
```
